# Results

Every number on this page comes from `bench/run-all.sh`. It writes raw
results to `bench/out/*.json` (the run below is archived in [`evidence/bench/`](evidence/bench/)), aggregates them into
[`metrics.json`](../metrics.json) and regenerates the section between the
markers below. To reproduce: `make bootstrap && make bench` (about 90 minutes).

## How each number is produced

| Metric | Script | Method |
|---|---|---|
| `idp_tp`, `idp_detect` | `bench/regressions.sh` | Five bad releases go through git (a commit to a scratch branch the tenants app follows): 20 % and 5 % HTTP 500, +400 ms on every request, +1 s on 5 % of requests, crash after 45 s. Detection time is from the moment a new canary ReplicaSet appears to the rollout's abort. After each case the change is reverted and the rollout must return to the previous stable revision. |
| `idp_clean`, `idp_false_rb`, `idp_lead` | `bench/clean-releases.sh` | Five releases that change only `RELEASE_ID`. Lead time is from the commit's timestamp to full promotion. It includes the Argo CD refresh (triggered like a webhook would) and the fixed canary pauses of 3 + 1 + 1 minutes, so roughly 5.5 minutes is the floor by design. |
| `zt_adm_p99` | `bench/admission.sh` + `bench/admission-k6.js` | k6 ramps to 500 VUs (30 s), holds 60 s; each VU creates a pod with `dryRun=All` through the API server, then waits 1 s. Every request runs the whole admission chain (Kyverno mutate with signature and provenance verification and digest pinning, Kyverno validate, CEL VAP) against 3 Kyverno admission replicas. Kyverno's verification cache is warmed with one request first. |
| `zt_attacks` | `bench/attacks/run.sh` | Five attacks as server-side dry runs in a tenant namespace, plus a baseline pod that must be admitted: unsigned image, tag moved to a tampered digest after signing, image validly signed by a different workflow with a forged SLSA predicate claiming the official builder, privileged container, hostPath mount. Each rejection must come from the expected control. |
| `zt_rot` | `bench/svid-rotation.sh` | **The SPIRE default X.509-SVID TTL is lowered from 1h to 5m for this test only**, and the demo-api pods are restarted to pick it up. An in-cluster client with its own SPIFFE ID then makes 20 mTLS requests/s (new TLS 1.3 handshake each) for 15 minutes across the 4 demo-api pods. Afterwards the root app restores the 1h TTL from git. |
| `zt_controls` | `bench/render.sh` | Distinct controls (C1…) in the [compliance map](compliance/nis2-dora-map.md). |

Environment: one workstation running everything (WSL2, 10 vCPUs, 12 GB for
the VM), so the kind cluster (1 control plane and 3 workers), Argo CD,
Kyverno, SPIRE, Prometheus, the load generator and k6 all compete for the
same CPUs. Absolute latencies are therefore pessimistic compared to a
cluster with dedicated nodes. Relative behaviour, such as which control
fires and whether a rollback happens, does not depend on that.

## Interpretation

**Rollback.** Every bad release was aborted and every clean one promoted.
Error and latency regressions were caught about 160 s after the canary
appeared. That time is set by the analysis cadence: 30 s initial delay, one
measurement per minute, abort on the third failure. The 5 % error case shows
why there are two burn tiers. Its burn rate (10×) is below the fast tier's
14.4×, so only the slow tier caught it; a single-threshold gate tuned for
fast burns would have promoted it. The crash loop took longer (219 s)
because restarts need time to accumulate. Clean releases took about 356 s
from commit to promotion. About 330 s of that is the deliberate canary
schedule (3 + 1 + 1 min of pauses plus pod start-up). Argo CD picked up
each commit within seconds because the bench triggers a refresh the way a
webhook would. With plain 60 s polling, add up to a minute.

**Admission latency: target missed on this host.** The 650 ms p99 target
at 500 VUs was **not met**: p99 was 11 s at 162 requests/s. No request
failed, and every admitted pod was pinned to its verified digest, so this
is a throughput ceiling, not a correctness problem. The sweep puts the
knee between 200 VUs (150 req/s, p99 177 ms) and 300 VUs (185 req/s, p99
3 s). Prometheus during the 500-VU run showed the cause:
- each of the three Kyverno admission replicas used about 1.7 cores;
- the API server used about 3.7 cores;
- the 10-vCPU host was about 70 % busy, with k6 itself on the same machine.

Kyverno's reference figure comes from dedicated nodes. Here the whole chain
shares one workstation, and every request runs two webhook calls with
signature and provenance checks (served from Kyverno's verification cache)
plus the CEL policy. Up to about 150 pod creations per second, p99 stays
under 200 ms. That is far above what a real tenant namespace generates, but
`zt_adm_p99` reports the 500-VU result as measured.

**Supply chain.** All five attacks were rejected by the control meant to
catch them, and the baseline pod was admitted. The foreign-builder image
carries a valid Sigstore signature from another workflow in the same
repository, plus a forged SLSA predicate that names the official builder.
It was rejected only because the signer identity did not match.

**SVID rotation.** With a 5-minute TTL (test only), 17,999 requests over
15 minutes each opened a new TLS 1.3 handshake. The client rotated its SVID
6 times and the four servers rotated theirs 24 times, with zero failed
handshakes. The TTL was restored to 1h afterwards.

**What the benches caught on the way.** Two of the fixes in the git history
were found by these runs:
- the registry policy blocked pod deletion, because CEL had no object to
  read on DELETE (`b36865b`);
- the scratch-branch handoff raced a root-app sync and sent a duplicate key
  to kustomize (`1125209`).

Earlier runs that hit these bugs were discarded, and the numbers above come
from the fixed scripts.
